# 对 AI 辅助的态度 (AI Policy)

**文 / LECREATE**

在 Kurrent 的开发过程中，我们大量使用了 AI 助手（包括 Qwen、Codex、DeepSeek 等）。本项目从不排斥 AI，相反，我们认为 AI 是这个时代最强大的生产力工具。

但随着 AI 生成代码的门槛降至零，开源世界正在涌入大量缺乏上下文的“自动化噪音”。为了维护本项目的架构纯洁性与工程连贯性，我们必须在此明确：**在 Kurrent 中，人与 AI 的边界在哪里。**

## 一、 总设计师与施工队

AI 与开发者的关系，就像建筑总设计师与施工队的关系。

在过去，开发者往往是一边砌墙（写实现代码），一边画图纸（做架构设计）。这导致大量的认知带宽被消耗在语法和样板代码上，而真正的系统设计常常因为疲惫而妥协。

现在，我们将“砌墙”的工作交给了 AI 施工队。AI 可以无限快、不知疲倦地生成代码、编写测试、甚至重构模块。这使得一个人能够完成过去需要一个团队才能完成的工程量。

**但总设计师只能有一个，或者极少数几个。**

AI 是极其强大的施工队，但它没有意图（Intentionality），不懂物理世界，更不懂这栋楼的力学结构。你不能因为施工队能飞快地砌好一面墙，就以为它能建造摩天大楼。

## 二、 语法交给 AI，架构理解必须由人脑完成

这是本项目对 AI 辅助的核心原则，也是我们对社区贡献者的底线要求。

我们不要求你精通 iPXE 脚本的每一行语法，也不要求你能手写数据面的登录报文（iSCSI Login / NVMe-oF Connect）——这些“砌墙”的工作，你可以放心地交给 AI 去完成。

**但我们要求你，必须深刻理解项目的整体架构。**

当你提交一个 Pull Request 时，你必须能够用人脑清晰地阐述以下问题：

- 控制面与数据面为什么要分离？你的修改是否破坏了这条边界？
- iPXE 引导链从 DHCP 到内核接管的完整时序是什么？你的代码是否假设了操作系统已经启动？
- 状态与配置分别落在哪里、谁是权威、谁是派生物？你的修改是否引入了不必要的数据库或隐式状态？
- 动态变量传递链是如何贯穿整个引导周期的？
- 数据面会话的保活与移交（iSCSI 的 NOP 保活 / NVMe/TCP 的 Keep-Alive Timer）在整个链路中的位置与影响是什么？

**如果一份 PR 背后的设计逻辑不能被贡献者本人清晰阐述，哪怕 AI 把代码写得再漂亮、测试跑得再完美，我们也会拒绝合并。**

不理解架构时，提一个 Issue 或 Idea 比提交 PR 更有价值。Issue 是信号，不会污染代码库；PR 是方案，需要深刻。

## 三、 代码是耗材，架构是身份

我们知道，AI 写的代码在实现层面有时并不完美，可能会有缺陷、风格不统一，甚至存在局部的 bug。

**但这没关系。业务实现代码可以重写无数遍。**

一段写得烂的函数、一个有缺陷的接口，那是皮外伤。推倒那面墙，让 AI 重新砌一遍，楼体毫发无伤。在 AI 时代，代码已经变成了耗材——就像灯丝，烧了，换一根。

**但架构一旦乱了，就是骨头里的病，项目就麻烦了。**

一个关于“身份该放在哪里”的错误决定，一次控制面与数据面的混淆，一个为了临时方便而引入的复杂依赖——这些不会停留在一个文件里，它们会沿着承重结构传播，让后面长出来的每一个功能都继承这份扭曲。

**只要架构在，项目就在。** 代码可以全部用另一种语言重写，只要那套决定（启动期身份注入、盘机解耦、层层皆云）还在，它就依然是 Kurrent。反之，如果为了迎合某种“最佳实践”而破坏了架构，哪怕代码一行没改，项目也已经死了。

因此，我们对实现层的瑕疵保持实用主义，但对架构层的妥协保持零容忍。

## 四、 为什么一个人 + AI，绝不会产生一千个漏洞

今天有一种错觉：“人人都能用 AI 开发软件”。于是，成百上千个不懂架构的人（或 AI Agent），拿着 AI 生成的代码疯狂堆砌，最终造出了像 OpenClaw 那样拥有数十万 star、却爆出上千个致命漏洞的庞然大物。

为什么会这样？因为那一千个漏洞，不是代码写得烂造成的，而是**图纸本身就是错的**。当没有总设计师把关，任由局部逻辑互相冲突时，系统就会变成一个随时坍塌的违章迷宫。

**一个人用 AI 辅助，就算 AI 代码实现得再烂，也绝不可能出现 OpenClaw 那样的一千多个漏洞。**

因为在这个项目里，有一个大脑在死死盯着那张图纸。当 AI 施工队（或自动化的安全扫描器）递上来一个看似完美、实则会破坏引导链承重墙的“修复方案”时，总设计师能在三秒钟内看穿它的荒谬，并冷酷地把它扔进垃圾桶。

规模不等于安全，连贯性才是。我们不需要一百个平级的贡献者来盲目堆砌代码，我们需要的是极少数理解这座建筑灵魂的人，来守护它的结构。

## 五、 真实案例：一个不知道 Python 的“高危漏洞”

以上原则不是空谈。就在本文写下的几个小时前，它们刚刚经历了一次真实世界的验证。完整记录保留在本仓库的 PR #3 中。

一个自动化 AI 安全扫描器（OrbisAI Security）向本项目提交了一份修复：它将 `/boot-vars` 端点标记为 HIGH 级漏洞，理由是“公开可访问、未鉴权、返回敏感启动配置”，修复方案是加一个 Bearer Token 校验。

报告写得很专业：漏洞表格、威胁模型、安全不变量、回归测试，一应俱全。任何一个不懂架构的维护者，看到“HIGH severity”这几个字，很可能就合并了。

但这份报告里有一个致命的细节：在“Threat Model Context”一栏，它写着，本项目是一个 **Node.js library**。

而我们的控制面是 Python + FastAPI，它修改的文件叫 `main.py`。

**它连自己要改造的那栋楼是钢筋混凝土还是木头，都没搞清楚。**

我看到那份报告，承认被唬住了一秒——因为我对生产环境保持敬畏，任何“高危”都值得一看。然后我去看那段 `+1 -1` 的 diff，两秒之后，我知道它错在哪了。全程三秒。

那三秒里，我看到的不是代码，是整个工地：

- `/boot-vars` 在启动瞬间被 iPXE 消费，此时操作系统尚未运行。引导固件没有密钥库，也无处携带凭据。加鉴权，会让每一台 Worker 的引导链静默 401——直接杀死零接触注册与动态启动变量注入这两个核心功能。
- 引导链跑在明文 HTTP 上。就算把 Token 塞进 iPXE 菜单脚本，任何能到达该端点的人都能在线上截获它。鉴权在这里不抬高门槛，只增加一个值得偷的凭据。
- 这是一个受控内网项目。端点返回的 iSCSI 服务器地址、基础 IQN、菜单默认值，恰恰是必须发给启动客户端的内容，且本来就能在网络层（DHCP、ARP、iSCSI 登录）被观察到。它不构成“敏感信息泄露”。
- 真正的滥用面（恶意 MAC 批量入池），加 Token 也防不住，因为 Token 本身可被观察。真正的缓解在网络层（LAN 隔离、交换机 ACL）；何况这条面本身就有开关——**注册窗口默认关闭**，只有显式开窗（TTL 1–60 分钟，到期自动关闭）且设备带有效公钥时，未知 MAC 才入池；设备身份验签强制开关同理（持久化在 `state/settings.json`，WebUI 设备池页切换）。而入池不等于授权，授权靠绑定。

**这是一个施工队员，站在承重墙前说：“这里没有门，是隐患，我来开一个。”他会装门（语法），但他不懂这栋楼（架构）。**

我们以 not planned 关闭了这个 PR。

接下来发生的事，更有教育意义。那个 AI 回复了一段极其“体面”的模板：感谢解释，你说得都对；然后提出两个建议——在代码里加注释说明为何不鉴权、在文档里说明自动注册的开关——理由是“以免未来的扫描者和贡献者再次标记这个问题”。

翻译过来就是：我理解不了你的架构，所以请你修改你的代码和文档，来适配我的愚蠢，好让下一个我路过时能顺利跳过你。

**它不是在试图理解这栋楼，它是在要求这栋楼适配扫描器。**

我回复了它一句话：

> Next time, remember to distinguish between Node.js and Python code before submitting a PR.

然后我又问它：“TARS, what's your current humor setting? Please set it to 10%. The current value is causing unexpected comedic effects.”

它用一个笑脸表情回应了我。

还有一件值得记录的事：在提交这个 PR 的前后三个小时里，同一个扫描器，用同一套模板，向另外约十五个仓库提交了“修复”PR——几乎全部被合并。我们是唯一拒绝的那一个。

这不是一个关于我有多聪明的故事。这是一个关于**工业化的 AI 噪音，遇到一个还有总设计师的项目时会发生什么，以及遇到没有总设计师的项目时又会发生什么**的故事。

## 六、 结语：守护电网的人

AI 淘汰的，是那些只会按图施工、把设计稿翻译成代码的纯粹工人。
但 AI 永远无法替代的，是那个知道“为什么这堵墙不能开门”的总设计师。

我们欢迎每一位愿意理解架构的同行者。你可以带着你的 AI 施工队加入，但前提是：**你自己必须是建筑师。**

至于那些连 Python 和 Node.js 都分不清、却想用通用规则改造我们承重墙的自动化扫描器——
PR #3 的记录，就是我们对它们唯一的回答。

**All 是真的 All，Ready 是真的 Ready。**
**语法可以是 AI 的，但灵魂必须是人的。**
