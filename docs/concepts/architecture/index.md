# 架构总览

Kurrent 把物理设备、存储节点与控制面组织成一套可启动、可迁移的计算系统。操作系统存放在网络存储上，机器经网络启动，身份与数据跟着 Worker 走。设备本身不保存持久状态：上电后经网络完成身份校验，取得系统盘的位置与启动参数，把远端磁盘当作本地根设备启动。系统盘由存储节点提供，启动后的块读写直接发生在设备与存储节点之间。

![架构：控制面节点、存储节点与设备之间的管理面、引导与数据面](/diagrams/zh/architecture.svg)

## 控制面与数据面

部署里的组件分属两个面：

- **控制面**负责管理：身份认证、资源调度与配置下发，全部经 HTTPS 进行。
- **数据面**负责实际的磁盘读写：设备与存储节点之间的 NVMe-oF（基于网络的 NVMe 块存储协议）流量，不经过控制面。

这种划分把故障隔离开：控制面只参与开通与引导，系统启动完成后，控制面是否存活不再影响磁盘读写。Worker 的盘流量在设备与存储节点之间直连（TCP 4421 端口，强制 TLS 1.3 加密），控制面故障只影响新的开通流程，不中断进行中的 I/O。管理操作统一从 nginx 的 443 端口进入，数据面不依赖控制面进程存活。

## 三个角色

### Controller（控制面）

Controller 是管理中枢，决定谁能启动、启动哪块盘、盘放在哪里。

- 控制面 HTTP 服务只监听容器内的 unix socket（本机进程间通信套接字），不直接暴露网络端口；nginx 以 443 端口作为统一管理入口，提供 WebUI 与管理面 API。
- 签名固件的引导请求走独立的 4443 端口，nginx 在这个入口只转发 `/boot-vars`、`/devices/report`、`/devices/challenge` 三个引导端点，把引导流量与管理流量隔开。
- 80 端口只做一件事：把 HTTP 请求重定向到 HTTPS。
- dnsmasq 以 host 网络模式运行，提供 DHCP、TFTP 与引导文件分发，是设备开机后最先接触到的服务。

状态以纯文件（YAML / JSONL）持久化在仓库外的状态根目录（`control-plane/state/`、`control-plane/config/`、`control-plane/dnsmasq/`），当前没有数据库。文件形式让状态可以直接查看、备份与迁移。控制面声明是唯一的权威输入，`dnsmasq.conf` 等派生文件在启动时按声明渲染，不手工维护。

WebUI 与 CLI 都只是 REST API 的客户端，不直接读写状态文件；状态位置与代码仓库解耦，移动仓库不影响运行中的系统。

### Storager（存储节点）

Storager 负责保存系统盘并对外提供块设备访问。每个节点运行两个组件。管理盘文件不需要内核特权，配置内核 NVMe 目标端需要，两者的权限要求不同，因此分开部署。

- **API Agent**：监听 4840 端口，要求双向 TLS 认证（mTLS，通信双方都出示证书），只接受控制面的调用。它负责盘文件的生命周期、母盘扫描与 reflink 克隆（文件系统级的秒级复制），并驱动本机存储后端。
- **nvmet-host**：不监听网络端口，只通过共享卷上的 unix socket 提供同样要求 mTLS 的管理接口。它把收到的指令翻译成内核 configfs 操作，并把 TLS 预共享密钥注入内核的 `.nvme` keyring（内核密钥环）。

数据面监听 4421 端口，强制 TLS 1.3 加密，固件引导阶段与操作系统内核阶段共用这一个端口。

存储后端以 nvmet（Linux 内核的 NVMe 目标端实现）为首选。iSCSI 后端代码仍然保留，但主分支已没有存活的引导路径；后端之间的差异封装在 Agent 内部，控制面不感知。

### Devices（计算设备）

Devices 是无状态的计算侧。物理设备不保存任何持久状态，启动过程只有两步：

1. PXE 网络引导时上报硬件指纹（MAC、UUID、SMBIOS、CPU、内存、网卡等 11 个字段），进入设备池等待分配。
2. 管理员把它绑定到某个 Worker、并为该 Worker 准备好系统盘后，设备以 NVMe-oF 远端磁盘为根设备启动。

启动之后，块读写直接走数据面，不经过控制面。

## 三实体模型

一台可启动的系统由三个实体组成：

| 实体 | 身份 | 说明 |
| --- | --- | --- |
| 设备（Device） | MAC（唯一） | 物理机器，台账条目；绑定关系的权威记录在设备侧 |
| Worker | `worker_id`（即主机名） | 计算身份；设备绑定后成为该 Worker 的引导节点 |
| 系统盘（System Disk） | NQN | 存储卷（母盘克隆或空白盘）；每个 Worker 可挂多块 |

NQN（NVMe Qualified Name）是 NVMe 子系统的全局唯一名称，系统盘以它为权威标识；iSCSI 使用的 IQN 由 NQN 派生，不单独维护。

三个实体各自独立替换：解绑或换绑时设备回池，系统盘保留在 Worker 上；一台 Worker 可以挂多块系统盘，默认启动的系统可以在线切换。Worker 的 `readiness` 只取决于两个条件：有没有绑定设备、有没有系统盘。实体模型的完整说明见[设备、Worker 与系统盘](../entities.md)。

## 数据流

管理请求从 443 端口进入，由 nginx 完成证书校验后转发给控制面；开通操作则由控制面主动推送到存储节点。两条路径都不经过数据面端口。

### 管理请求

浏览器或 CLI 的请求先到 nginx。nginx 校验客户端证书链与 CRL（证书吊销列表），只有校验通过才把请求者身份写入身份头，再经 unix socket 交给控制面。控制面依次执行凭据认证、主体分类与权限判定，然后读写台账、记录审计，需要时调用存储节点的 Agent。

身份头只在 nginx 注入时可信；其他代理位置默认清空身份头，防止外部伪造。

```text
浏览器 / CLI
  → 443 nginx
      → mTLS 校验（users/nodes 信任包 + CRL）
      → 注入身份头（仅 SUCCESS）
  → unix socket 控制面
      → 认证器链（证书 / token / 会话）
      → 主体类与 RBAC
      → 台账 / 审计 / 调用 Agent
```

### 开通与凭据

建盘、挂载等开通操作由控制面发起：控制面经 4840 端口以 mTLS 调用 Agent，Agent 再经共享卷上的 unix socket 调用 nvmet-host，由后者写入内核 configfs 并返回结果，TLS 预共享密钥同时写入内核 keyring。

建盘时控制面同步签发绑定该 Worker 的认证密钥（DHHC-1 格式，NVMe-oF 的挑战握手认证密钥）。推送失败会记录在台账中，由后台对账线程周期性重试，直到送达为止。

```text
控制面
  → 4840 Agent（mTLS）
      → UDS nvmet-host（mTLS）
          → configfs：subsystem / namespace / port / allowed_hosts / dhchap_key
          → 内核 .nvme keyring：TLS PSK
```

## 引导链路

设备启动从 DHCP 与 TFTP 开始：设备先取得 iPXE 引导程序与脚本指针，再经 HTTPS 取回后续配置。

设备身份来自 TPM 2.0 芯片内一把不可导出的证明密钥（AK）。每次引导，固件用这把密钥对 PCR 0/2/4/7 生成 quote，证明自己运行在预期的平台上。PCR 是记录固件与启动配置的平台寄存器，quote 是 TPM 对这些寄存器当前值的签名报告。未知 MAC 只有在注册窗口开启、携带有效 AK 且 Secure Boot 开启时才进入设备池。

控制面的 `/boot-vars` 端点依次校验绑定关系、quote 签名、一次性随机数（nonce）与平台基线，全部通过才下发启动参数：根设备路径、盘 NQN 与连接凭据。设备随后以 DH-HMAC-CHAP 挑战握手完成连接认证，并以 TLS 1.3 加密传输。

固件在移交操作系统前把凭据写入 NBCT 表（ACPI 中的凭据传递表），initramfs 读取 NBFT 与 NBCT，用同一套凭据重新连接存储并挂载根文件系统。盘内不包含任何固定的机器身份，因此同一块盘可以在不同机器上启动。

```text
设备
  → DHCP / TFTP（首跳）
  → HTTPS：脚本、设备上报、挑战、/boot-vars
  → 4421：NVMe/TCP + TLS 1.3，认证与 I/O
  → NBFT / NBCT → initramfs
```

控制面只在 HTTPS 段参与；进入数据面后，设备直连存储节点。逐步细节见[引导链](../boot-chain.md)。

## 安全边界

管理面支持三种凭据，按顺序尝试：mTLS 客户端证书、管理 token 与服务端会话。任何一种验证成功，都会得到统一的请求者身份，供后续的主体分类与权限判定使用。

凭据由三个独立的根证书机构（CA）签发，分别覆盖用户（users）、组件（nodes）与控制面自身（control）。每个信任域的密钥泄露只影响该域。nginx 只信任 users 与 nodes 的公钥包，按证书签发者判定主体类别；控制面的每个路由声明接受哪些主体类别，未声明的一律拒绝。

每个管理请求都写一条审计记录；审计写盘失败时请求返回 503：宁可拒绝操作，也不放行无审计的管理动作。

设备身份的信任根由四部分共同构成：TPM 内的 AK、绑定一次性 nonce 的 PCR quote、平台基线，以及绑定关系本身。设备必须绑定到某个 Worker，才能取得该 Worker 的启动凭据。指纹上报端点不鉴权，只用于发现设备，不产生任何权限。

认证与加密是彼此独立的两层：DH-HMAC-CHAP 完成连接认证，TLS 1.3 保护传输内容。TLS 的预共享密钥由认证密钥派生，吊销认证密钥即同时吊销加密资格，没有明文回退。完整威胁模型见[安全模型](./security.md)。

## 状态与派生物

控制面声明与节点声明是系统仅有的两份输入：前者定义网络、证书体系、注册窗口与引导策略，后者定义数据目录、存储后端与 NQN 命名域。其余配置都由它们派生，避免多处维护同一事实。

运行时状态位于状态根目录 `<state>`，默认 `~/.local/state/kurrent`，由 `~/.kurrent/deployment.yaml` 固定。台账、会话、token、审计与证书材料都存放在这里，与代码仓库解耦。

信任材料同样位于状态根：

- 三个根 CA（users、nodes、control）分别签发人员、组件与控制面证书。
- 服务器证书与 CRL 供 nginx 使用；引导链的信任锚是构建时内嵌在固件里的引导 CA。
- 节点侧的身份、引导凭据、组件证书与日志位于 `<state>/storager`。
- 首次部署的管理凭据经 `<state>/control-plane/bootstrap` 一次性交换交给部署用户，交换包消费后即删除；权威凭据 `admin.conf` 始终留在控制面状态目录。

派生物从权威单向生成：dnsmasq 配置由网络声明渲染，引导菜单与默认盘由控制面投影，WebUI 与引导脚本来自仓库构建。修改权威后派生物随之更新，反向修改派生物不会生效。

系统当前没有数据库，控制面为单节点纯文件存储。状态备份、文件权限与单机故障边界由部署方承担。状态外置之后，移动代码 checkout 不再影响台账与引导身份。

## 端口

端口按归属划分，便于确定每台主机需要暴露哪些服务。

### 控制面宿主

| 端口 | 协议 | 用途 |
| --- | --- | --- |
| 53 | UDP/TCP | dnsmasq DNS |
| 67 / 69 | UDP | DHCP / TFTP |
| 80 | TCP | 仅 301 升级到 443 |
| 443 | TCP | 管理入口：WebUI、管理面 API 与未签名调试脚本 |
| 4443 | TCP | 引导 HTTPS：`/boot-vars`、`/devices/report`、`/devices/challenge`，只对引导网段放通 |
| — | unix socket | 控制面管理面；nginx 与健康检查访问 |

控制面进程本身不监听 TCP 端口，也不挂载 `docker.sock`。

### 存储节点

| 端口 | 协议 | 用途 |
| --- | --- | --- |
| 4840 | TCP | Agent HTTPS（mTLS，控制面调用） |
| 4421 | TCP | NVMe/TCP 数据面，强制 TLS 1.3；固件段与内核段共用 |
| — | 共享卷 UDS | nvmet-host 管理面（mTLS） |
| 3260 | TCP | iSCSI 兼容后端（主分支无存活引导路径） |

4840 只接受控制面的 mTLS 连接，4421 强制 TLS 1.3。

### 设备

设备只需要能访问 DHCP、TFTP、HTTPS 与存储节点的数据面端口，不直接访问控制面管理面。

## 故障域

故障的影响范围由进程归属决定：数据面不依赖控制面存活，管理组件的故障因此不会波及正在运行的系统。

| 故障 | 影响 |
| --- | --- |
| 控制面停止 | 新开通、新引导、配置修改与审计停止；已建立的 NVMe/TCP I/O 继续 |
| nginx 停止 | 管理面与引导链 HTTPS 不可用；数据面不受影响 |
| dnsmasq 停止 | 新设备无法 DHCP/TFTP 引导；已运行系统不受影响 |
| 单个存储节点停止 | 该节点上的盘无法启动或 I/O 中断；其他节点不受影响 |
| 控制面宿主损坏 | 需要从备份恢复；丢失 PKI/证书会导致组件重新 enroll、设备重新信任 |
| 设备损坏 | 换绑到新设备；系统盘与 Worker 身份保留 |

## 协议演进

数据面已从 iSCSI 迁移到 NVMe-oF（NVMe/TCP）。固件主分支包含完整补丁集（`0001`–`0011`），整机冷启动已在多个发行版通过验收。

这次迁移没有改变架构语义：无状态计算、盘机解耦、从 MAC 到引导的身份链都不依赖具体传输协议。存储后端差异已由 Agent 抽象，更换传输层不触碰上层设计。iSCSI 在主分支已无存活的引导路径，历史实现保留在 `iscsi-classic` 分支。

## 扩展点

- 存储后端差异封装在 Agent 内部，控制面只发 HTTP 请求，新增后端不需要改控制面。
- 引导菜单、超时与默认盘由控制面投影，不写入盘内，因此调整启动行为不需要改盘。
- 固件由独立仓库按补丁构建，可在上游基线上重建。

后续方向（高可用、IPv6、ARM、数据盘）见[路线图](../../about/roadmap.md)。

当前架构是现有约束下作出的取舍，会随约束变化继续调整。目标是计算、存储与身份不再绑定单机，系统可以整体调度、迁移与重建；组件划分、协议与部署方式都可以随约束更换。
