# 首跳

首跳是从加电到取得一个可执行引导程序的这一段。它决定后续所有脚本的来源，所以必须先可信。问题在于：这一步的下载走的是明文 DHCP 与 TFTP，网络本身提供不了任何保护。因此可信性只能由目标机固件自己保证——由固件验证签名，不依赖网络中的任何声明。

## 取地址与下载

设备经 DHCP 取得地址与 `next-server`，再从 TFTP 下载首跳 `snponly.efi`。TFTP 根只暴露这个文件与 `boot.ipxe` 指针两份，不提供其他内容，把明文可下载的面收到最小。

替换 `snponly.efi` 后需要重启 dnsmasq 容器：容器以文件级挂载该文件，挂载固定的是原文件的 inode，直接覆盖文件内容不会反映到容器里。

## 验签

UEFI 用目标机 `db`（固件内置的受信签名证书库）中的站点证书验证 `snponly.efi`。镜像未签名、签名不符或被篡改时，固件直接拒绝执行，网络引导不会开始。

站点证书属于一次性预置：把证书写入目标机 `db` 是部署时执行一次的步骤，不随每次启动重复，也不依赖控制面在线。预置流程见 [Secure Boot 预置](../../firmware/secure-boot.md)。

## 内嵌脚本与 boot CA

签名镜像内嵌静态脚本、boot CA 与引导 HTTPS 端口。内嵌的意义是把这些内容一起纳入签名保护：攻击者即使控制了网络，也无法单独替换脚本或信任锚。控制面地址默认不入镜像，由 DHCP 提供。

首跳之后的菜单、变量与设备接口都经 4443 HTTPS 取回，只信任内嵌的这张 boot CA，不采用首次连接信任（TOFU，即第一次连上谁就信谁）。这样引导服务器无法被冒充。

## 失败

- 验签失败：固件拒绝执行，设备停在 UEFI 引导菜单。
- 4443 握手失败：固件构建使用的 boot CA 与控制面 `state/pki/ca/boot/ca.crt` 不一致，或叶证书的 SAN、端口与构建不一致。
- TFTP 或 DHCP 不可达：网络引导无法开始；这类失败只造成拒绝服务，不改变信任判断。
