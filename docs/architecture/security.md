# 安全模型

Kurrent 的安全边界不是一条线，而是四组彼此独立的信任：

| 边界 | 保护对象 | 信任锚 |
| --- | --- | --- |
| 管理面 | 谁可以调用管理接口 | users CA 证书 / 管理 token / 服务端会话 |
| 组件面 | 哪些存储节点组件可以加入与续期 | nodes CA + 绑定节点身份的 bootstrap token + CRL |
| 设备面 | 哪台机器可以取得某次引导的凭据 | 设备 NVRAM 私钥 + 注册窗口 + 绑定关系 + TOFU |
| 数据面 | 谁可以连接、内容是否加密 | DH-HMAC-CHAP + TLS 1.3 PSK |

四者不能互相替代。管理面被攻陷不等于设备可以冒领引导凭据；设备密钥泄露也不等于可以访问管理面。

## 威胁模型

### 假定的前提

- 控制面宿主、存储节点宿主与网络设备由受信任的运维方管理；宿主 root 被攻陷视为对应边界的失守。
- PXE 网段是独立信任边界，且由部署方完成二层防护。
- 设备物理访问受控；能够物理接触设备并重置 NVRAM 的攻击者不在本模型内。
- 运维人员按最小权限使用管理凭据；备份与密钥存储由部署方保护。

### 保护目标

- 未授权主体不能通过管理面读取台账、修改绑定、签发凭据或执行写操作。
- 未认领、未绑定或验签失败的设备不能取得其他 Worker 的引导变量。
- 已吊销的组件与用户不能继续通过 mTLS。
- NVMe/TCP 数据面内容在传输中加密；缺少凭据时拒绝引导，不回落明文。

## 管理面

### 入口收敛

- 唯一对外入口是 nginx `443`；控制面服务不监听 TCP，只监听容器内 unix socket。
- 身份头仅信任 nginx 注入；其他反代位置默认清空。若开放第二个入口或允许外部注入身份头，管理面认证即可被绕过。
- 控制面容器不挂载 `docker.sock`。

### 主体类

nginx 按证书 issuer 判定主体类：

- users CA → `human`；
- nodes CA → `component`；
- control 域不进入 443。

每个路由声明接受的主体类，未声明的路由在启动期即失败。跨类访问返回 403：组件证书不能进入管理面，人类证书不能调用组件续期。

### 凭据

| 凭据 | 保护 |
| --- | --- |
| 人员证书 | 私钥由用户本地生成与保管；控制面只签 CSR；按序列号吊销 |
| 管理 token | 台账只存摘要；scope 收窄权限；TTL 与吊销 |
| 会话 | Cookie 只含 jti/exp/epoch；身份以服务端台账为准；可逐个吊销与全部下线 |
| 管理凭据交接 | 一次性交换目录：逐文件 SHA-256、目录 0700 / 文件 0600、属主对齐；CLI 自检通过才消费并删除副本，权威文件留在状态根 |

读请求只需已认证，写请求需要 `admin` 组；会话写请求额外做同源校验。

### 审计

每个管理请求写一条审计记录；写入失败时请求返回 503（fail-closed），不允许在失去审计能力时继续执行写操作。告警覆盖凭据注入未验签、跨类访问、未知 issuer/CRL、认证失败风暴、bootstrap 身份不符、证书与 CRL 变更、用户文件变更与审计失败。

## 组件面

- 组件证书由 nodes CA 签发；首次加入需要绑定 `agent_id` 的 bootstrap token，默认一次性。
- 组件在到期前 renew；控制面校验对端证书的序列号与 CRL。
- 组件周期拉取 nodes CRL；CRL 缺失或过期时 fail-closed，不降级放行。
- 吊销组件会同时删除其 bootstrap token，堵住“吊销后立刻换发新证书”的窗口。
- 被吊销节点通过重新签发 token 与 `kurrent join` 恢复；恢复过程无需手工删除旧证书。

## 设备面

### 锚点

- 设备私钥在 NVRAM 内生成并持久化（ECDSA P-256），私钥不出机器。
- 注册窗口只决定“是否入池”，不授予引导权限。
- 绑定关系是设备侧的 `bound_worker_id`；`/boot-vars` 校验请求 MAC 是否属于该 Worker 的绑定设备。
- 挑战-应答使用一次性 nonce 与 ECDSA 签名；验签强制开启后，无密钥、无签名或验签失败一律拒绝。
- 服务器证书 TOFU：首次握手固定叶证书指纹，后续不匹配即拒绝。

### 明确的边界

1. **首跳没有密码学保护**。DHCP 与 TFTP 上的 `snponly.efi`、`boot.ipxe` 由设备固件直接信任。同一二层内的攻击者可以伪造 DHCP/ARP、替换首跳文件。部署要求把 PXE 网段隔离，并启用 DHCP snooping、动态 ARP 检测、RA guard 与端口安全；这是部署边界，不是产品内部的密码学闭环。
2. **设备密钥是持有者凭证**。挑战-应答证明“请求方持有该私钥”，不证明“运行该私钥的代码可信”。启动后的系统若能读取固件变量，也能使用该密钥。主线固件未签名、未使用 TPM 度量，因此这一路径目前没有产品内的闭包。
3. **TOFU 首次信任**。首次连接时不校验 CA，而是固定叶证书指纹；第一次握手可能被中间人利用。控制面证书轮换后，设备必须重新信任，否则拒绝连接。
4. **物理访问**。能够接触设备并重置 NVRAM 的攻击者可以清除密钥与指纹，退化为“未注册设备”。这种设备仍受注册窗口与绑定约束，但原身份锚点已丢失。

### 首跳安全的决策

首跳指 DHCP → TFTP `snponly.efi` → TFTP `boot.ipxe`。设备固件直接信任其内容，iPXE 此时也尚未取得控制面证书，因此这段没有可用的密码学锚点。主线不尝试在产品内为这段建立认证，而是把 PXE 网段本身作为信任边界；该决策只在部署满足边界条件时成立。该决策不表示首跳风险已在产品内解决，它说明风险由谁承担、在什么条件下可以接受。

首跳完整性由部署方保证：PXE 网段独立于办公网与存储数据面，控制面是该网段唯一的 DHCP/TFTP 提供者，接入交换机启用 DHCP snooping、动态 ARP 检测、RA guard 与端口安全，有条件时启用 802.1X/MAB。TFTP 根只保留 `snponly.efi` 与 `boot.ipxe`；配置、菜单与设备端点从 HTTPS 取回。首跳之后的链路由产品机制保护：设备 NVRAM 私钥、注册窗口、绑定关系、服务端 TOFU、挑战-应答与数据面 TLS。这些机制不能替代首跳保护。注册窗口只决定设备是否入池，不是首跳保护；验签强制开启后，未持有设备私钥的请求不能取得引导凭据，但同二层攻击者仍可替换首跳文件，借用设备的签名能力。

之所以如此，是因为设备固件不提供可移植的首跳验证：UEFI 网络引导直接信任 DHCP/TFTP 内容，主线 iPXE 未签名；没有硬件信任根，产品内就没有可用的密码学闭环。同时，把站点 CA、签名密钥或设备指纹预置到每台设备，会把零接触入池变成逐台预置，与项目的接入模型冲突。更根本的是，首跳认证只能关闭一部分路径：即使首跳被签名与固定 CA 保护，启动后的系统仍可读取设备私钥；完整闭环还需要 TPM 度量或等价机制。明确边界比不完整地宣称“已解决”更可靠，部署方需要知道哪些风险由产品承担、哪些由网络边界承担。

同一二层内的攻击者可以伪造 DHCP/ARP、替换首跳文件，把设备引向伪造的控制面或存储端；首次接触时 TOFU 会固定伪造证书。攻击者还可以替换首跳文件，使设备在真实控制面上完成一次合法签名，再取走 `/boot-vars` 返回的 DHHC-1 与 TLS PSK，随后以该设备身份连接数据面并读取或改写系统盘。该路径在产品内没有密码学闭环，能约束它的是上述部署边界。二层接入控制限定哪些端口可以接入，但不认证 DHCP/TFTP 内容；已授权端口上的攻击者仍可伪造 DHCP/ARP。若部署无法提供该边界，首跳风险不被缓解，该部署不应视为满足本安全模型。

替代方案也没有改变这一结论。把站点 CA 固定在母盘或首次预置中，并不能认证 DHCP/TFTP 首跳：母盘是操作系统盘，盘内固定不影响固件；首次预置到 NVRAM 也只保护 iPXE 之后的 HTTPS 段。只设置 `trust` 不会关闭 TOFU，要关闭首次接受需要在构建期固定信任锚并禁用 TOFU 接受路径。Secure Boot、TPM 度量与单密钥 UKI 的取舍见下一节。

### Secure Boot 路线的探索

首跳风险的另一条思路，是把信任锚前移到 UEFI 固件：用 Secure Boot 验证首跳代码，再用固定 CA 验证控制面的 HTTPS 证书，使首跳获得密码学保护，而不只依赖 PXE 网段隔离。该路线在独立分支上完成过实现与验收。站点签名 iPXE 并把公钥预置到目标机 UEFI 信任库，引导脚本嵌入签名后的 iPXE，TFTP 只交付签名二进制。构建期用 `TRUST=`/`CERT=` 固定控制面引导 CA，并关闭 TOFU 首次接受。系统盘使用发行版签名的 shim/GRUB 链。QEMU/OVMF 上已验证从签名 iPXE 经 sanboot、GRUB 与内核 lockdown 到 `login:`，首跳替换与伪造 HTTPS 服务器均被拒绝。目标机型的逐型号验收尚未完成。

该路线关闭了首跳替换与伪造服务器，却没有关闭设备私钥被启动系统读取。私钥保存在带运行时访问权限的 EFI 变量中。系统盘使用的发行版签名 shim/GRUB 链允许未签名的 `grub.cfg` 与 initrd，因此这条受信链也能启动读取私钥的系统。首跳被签名保护之后，攻击者仍可取得设备私钥并完成设备身份签名；这条路径不在 Secure Boot 的验证范围内。

没有继续推进，根本原因是它没有形成产品内的完整闭环：关闭首跳替换，却留下私钥读取，作为主线支持项会让“已启用 Secure Boot”被误读为设备身份已经完整闭环。该路线还要求逐站点预置：站点需自建签名密钥、签名 iPXE、把公钥写入每台目标机 UEFI 信任库，并准备发行版签名的 shim/GRUB；不同发行版与主板支持不一致，签名密钥与引导 CA 的生命周期也成为新的运维负担。这些是一次性预置，不是运行时依赖，但仍会把零接触入池变成逐站点准备。剩余的闭合路径还需要 TPM 度量/远程证明；单密钥 UKI 可以收敛可签名引导单元，但它本身不关闭私钥读取。这些都属于信任根与引导流程的重新设计，尚未完成端到端验收。

目前，Secure Boot 实现保留在独立实验分支，未合入主线；主线仍以 PXE 网段为信任边界并保留 TOFU。固件未签名，开启 Secure Boot 的目标机需要在部署前关闭它。需要首跳密码学闭环的部署，应等待能够同时关闭首跳替换与私钥读取的方案完成验收。

## 数据面

- 认证：DH-HMAC-CHAP，target 侧按 `allowed_hosts` 限制 Host NQN。
- 加密：TLS 1.3，单端口 `4421`，固件段与内核段共用。
- PSK 由认证密钥派生，不单独存储；轮换/吊销认证密钥即原子地轮换/吊销 PSK。
- PSK 在存储节点落入内核 `.nvme` keyring；`tlshd >= 1.5.0` 与进程 keyring 优先是避免旧钥遮蔽新钥的前提。
- nvmet 后端缺少密钥或端口未就绪时，控制面不下发完整引导变量；非 nvmet 后端不投影 NVMe-oF 凭据。`menu.ipxe` 在缺少必要变量时直接失败，不拼接明文 URI。

### 静态明文边界

DHHC-1、派生 PSK、设备私钥与 CA 私钥以明文形式存在于必要位置：

- 控制面状态文件（0600）；
- Agent 缓存（0600）；
- 存储节点 configfs 与内核 keyring；
- 设备 NVRAM。

Kurrent 不在应用层再加密这些位置。部署方需要负责磁盘/备份加密、宿主 root 边界与物理安全。

## 当前不解决的问题

- **首跳替换与同二层攻击**：按上文“首跳安全的决策”交给 PXE 网段隔离与二层防护；产品内无密码学闭环。
- **启动后读取设备私钥**：未使用 Secure Boot/TPM 度量，未签名固件。
- **控制面或存储节点宿主 root**：视为对应边界失守。
- **物理访问与 NVRAM 重置**：需要重新注册。
- **可用性攻击**：DHCP 池耗尽、认证端点限速与资源耗尽没有完整的抗 DoS 设计。
- **控制面高可用**：单节点、文件状态；宿主故障需要备份恢复。
- **密钥静态加密**：由部署方负责。

## 部署检查清单

- [ ] PXE 网段独立，控制面是唯一 DHCP/TFTP 提供者。
- [ ] 交换机启用 DHCP snooping、动态 ARP 检测、RA guard、端口安全；有条件时启用 802.1X/MAB。
- [ ] 控制面只暴露 22、53/67/69、80/443；存储节点只暴露 4840/4421（按需限制来源）。
- [ ] `sudo kurrent host check --strict` 无 FAIL、无 SKIP；CA 私钥、`admin.conf`、凭据与审计文件为 600。
- [ ] 注册窗口按需开启并设置放行额度，用后关闭。
- [ ] 验签强制在设备认领完成后开启。
- [ ] 人员证书按需签发，离职或泄露立即吊销。
- [ ] 定期检查 CRL 刷新、凭据推送与审计告警。
- [ ] 备份加密保存，并验证恢复流程。
- [ ] 固件产物来自可信来源并校验 `SHA256SUMS`。
