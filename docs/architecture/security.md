# 安全模型

Kurrent 的安全边界不是一条线，而是四组彼此独立的信任：

| 边界 | 保护对象 | 信任锚 |
| --- | --- | --- |
| 管理面 | 谁可以调用管理接口 | users CA 证书 / 管理 token / 服务端会话 |
| 组件面 | 哪些存储节点组件可以加入与续期 | nodes CA + 绑定节点身份的 bootstrap token + CRL |
| 设备面 | 哪台机器可以取得某次引导的凭据 | TPM AK + PCR 基线 + 注册窗口 + 绑定关系 + 签名首跳与固定 boot CA |
| 数据面 | 谁可以连接、内容是否加密 | DH-HMAC-CHAP + TLS 1.3 PSK |

四者不能互相替代。管理面被攻陷不等于设备可以冒领引导凭据；设备身份私钥不可导出，但仍不代表可以访问管理面。

## 威胁模型

### 假定的前提

- 控制面宿主、存储节点宿主与网络设备由受信任的运维方管理；宿主 root 被攻陷视为对应边界的失守。
- PXE 网段是独立信任边界，且由部署方完成二层防护。
- 设备物理访问受控；能够物理接触设备并清除 TPM 或重置固件信任库的攻击者不在本模型内。
- 运维人员按最小权限使用管理凭据；备份与密钥存储由部署方保护。

### 保护目标

- 未授权主体不能通过管理面读取台账、修改绑定、签发凭据或执行写操作。
- 未认领、未绑定或 TPM 证明未通过的设备不能取得其他 Worker 的引导变量。
- 已吊销的组件与用户不能继续通过 mTLS。
- NVMe/TCP 数据面内容在传输中加密；缺少凭据时拒绝引导，不回落明文。

## 管理面

### 入口收敛

- 唯一对外入口是 nginx `443`；控制面服务不监听 TCP，只监听容器内 unix socket。
- 身份头仅信任 nginx 注入；其他反代位置默认清空。若开放第二个入口或允许外部注入身份头，管理面认证即可被绕过。
- 控制面容器不挂载 `docker.sock`。

### 主体类

nginx 按证书 issuer 判定主体类：

- users CA → `human`；
- nodes CA → `component`；
- control 域不进入 443。

每个路由声明接受的主体类，未声明的路由在启动期即失败。跨类访问返回 403：组件证书不能进入管理面，人类证书不能调用组件续期。

### 凭据

| 凭据 | 保护 |
| --- | --- |
| 人员证书 | 私钥由用户本地生成与保管；控制面只签 CSR；按序列号吊销 |
| 管理 token | 台账只存摘要；scope 收窄权限；TTL 与吊销 |
| 会话 | Cookie 只含 jti/exp/epoch；身份以服务端台账为准；可逐个吊销与全部下线 |
| 管理凭据交接 | 一次性交换目录：逐文件 SHA-256、目录 0700 / 文件 0600、属主对齐；CLI 自检通过才消费并删除副本，权威文件留在状态根 |

读请求只需已认证，写请求需要 `admin` 组；会话写请求额外做同源校验。

### 审计

每个管理请求写一条审计记录；写入失败时请求返回 503（fail-closed），不允许在失去审计能力时继续执行写操作。告警覆盖凭据注入未通过证明、跨类访问、未知 issuer/CRL、认证失败风暴、bootstrap 身份不符、证书与 CRL 变更、用户文件变更与审计失败。

## 组件面

- 组件证书由 nodes CA 签发；首次加入需要绑定 `agent_id` 的 bootstrap token，默认一次性。
- 组件在到期前 renew；控制面校验对端证书的序列号与 CRL。
- 组件周期拉取 nodes CRL；CRL 缺失或过期时 fail-closed，不降级放行。
- 吊销组件会同时删除其 bootstrap token，堵住“吊销后立刻换发新证书”的窗口。
- 被吊销节点通过重新签发 token 与 `kurrent join` 恢复；恢复过程无需手工删除旧证书。

## 设备面

### 锚点

- 设备身份是 TPM 2.0 的证明密钥（AK）：私钥在 TPM 内创建、不可导出，启动后的系统无法读取。
- 注册窗口只决定“是否入池”；入池要求携带有效 AK 且 Secure Boot 处于开启状态，无 TPM 或 Secure Boot 未开启的设备被拒绝。
- 绑定关系是设备侧的 `bound_worker_id`；`/boot-vars` 校验请求 MAC 是否属于该 Worker 的绑定设备。
- 挑战-证明使用一次性 nonce 与 PCR quote；证明强制默认开启，无 AK、quote 无效、nonce 重放或 PCR 与基线不符一律拒绝。
- 平台基线在首次证明通过时记录（TOFU）；摘要变化必须由管理员批准后更新。
- 引导 HTTPS 固定信任签名固件内嵌的 boot CA（4443）：只接受该 CA 签发的服务器证书，不回落首次连接信任；boot CA 轮换等于重刷固件。

### 明确的边界

1. **首跳依赖 Secure Boot**。设备入池要求 Secure Boot 开启，首跳代码由 UEFI 信任库验证签名，TFTP 只交付签名二进制。签名固件与 AK 创建、quote 命令由固件仓交付；逐型号验收尚未完成。未开启 Secure Boot 的设备不能入池，部署不能靠关闭 Secure Boot 绕过首跳保护。
2. **设备身份的边界**。AK 私钥不可导出，证明覆盖 PCR 0/2/4/7 的启动度量；这不等于运行期系统可信：被控的操作系统仍可在轮换窗口内取得当前 PSK，并读取已挂载的系统盘。PCR 基线是 TOFU——首次证明若发生在攻击者控制下，基线会被污染，首次登记应核对装机环境。
3. **引导 HTTPS 的信任来自签名固件**。boot CA 在构建时烘进签名镜像，只用于签发 4443 叶证书；更换 boot CA 必须重新签名固件并在目标机重新预置 `db`，否则引导 HTTPS 一律失败。
4. **物理访问**。能够清除 TPM 或更换主板的攻击者会失去原 AK；这类设备退化为“未注册设备”，需删除登记并在注册窗口内重新入池，原身份不复活。

### 首跳与证明的分工

首跳指 DHCP → TFTP `snponly.efi`。UEFI 固件用目标机 `db` 中的站点证书验证首跳签名，未签名或篡改的镜像不会执行；静态脚本、boot CA 与控制面地址都嵌在这个签名二进制里，因此首跳内容不可单独替换。

首跳之后由两类机制接续：

- **服务器身份**：固件只信任构建时嵌入的 boot CA，引导 HTTPS 由该 CA 签发的证书锚定，不使用首次连接信任。
- **设备身份**：TPM AK 对 PCR 0/2/4/7 生成 quote，nonce 原样写入 `extraData`；控制面验签、验 nonce 一次性，并把 PCR 摘要与平台基线比对。私钥不可导出，启动后的系统无法复制设备身份到别处。

因此同二层攻击者能做的只剩拒绝服务：伪 DHCP/ARP 或链路中断可以让设备停住，但不能替换首跳、替换脚本或冒充引导服务器。攻击者若取得已入池设备的运行期控制权，仍可在轮换窗口内取得当前 PSK；缩短轮换周期与吊销是主要处置手段。

### 平台基线与固件变更

PCR 基线覆盖固件、Secure Boot 策略与启动配置。升级固件、修改 Secure Boot 密钥或调整启动项都会改变 PCR，证明按 `pcr_mismatch` 被拒，引导凭据停止下发。管理员核对变更后，在设备详情中批准设备最近一次上报的摘要，设备下次启动按新基线校验。该流程把“合法的平台变更”与“未知的度量漂移”分开处理，不提供静默放行。

## 数据面

- 认证：DH-HMAC-CHAP，target 侧按 `allowed_hosts` 限制 Host NQN。
- 加密：TLS 1.3，单端口 `4421`，固件段与内核段共用。
- PSK 由认证密钥派生，不单独存储；轮换/吊销认证密钥即原子地轮换/吊销 PSK。
- PSK 在存储节点落入内核 `.nvme` keyring；`tlshd >= 1.5.0` 与进程 keyring 优先是避免旧钥遮蔽新钥的前提。
- nvmet 后端缺少密钥或端口未就绪时，控制面不下发完整引导变量；非 nvmet 后端不投影 NVMe-oF 凭据。`menu.ipxe` 在缺少必要变量时直接失败，不拼接明文 URI。

### 静态明文边界

DHHC-1、派生 PSK 与 CA 私钥以明文形式存在于必要位置：

- 控制面状态文件（0600）；
- Agent 缓存（0600）；
- 存储节点 configfs 与内核 keyring。

Kurrent 不在应用层再加密这些位置。部署方需要负责磁盘/备份加密、宿主 root 边界与物理安全。

## 当前不解决的问题

- **首跳替换**：由 Secure Boot 验证签名固件关闭；未开启 Secure Boot 的设备不能入池。
- **引导服务器冒充**：由签名固件内嵌的 boot CA 关闭，不回落首次连接信任。
- **引导面拒绝服务**：伪 DHCP/ARP 与链路中断仍可阻断引导，没有完整的抗 DoS 设计。
- **运行期被控**：TPM 证明不保护运行期；被控系统可在轮换窗口内取得当前 PSK。
- **平台基线与固件验证**：逐型号（独立 TPM / AMD fTPM）的 PCR 行为与签名固件验收尚未完成。
- **控制面或存储节点宿主 root**：视为对应边界失守。
- **物理访问与 TPM 清除 / 更换主板**：原 AK 丢失，需删除登记后重新入池。
- **可用性攻击**：DHCP 池耗尽、认证端点限速与资源耗尽没有完整的抗 DoS 设计。
- **控制面高可用**：单节点、文件状态；宿主故障需要备份恢复。
- **密钥静态加密**：由部署方负责。

## 部署检查清单

- [ ] PXE 网段独立，控制面是唯一 DHCP/TFTP 提供者。
- [ ] 交换机启用 DHCP snooping、动态 ARP 检测、RA guard、端口安全；有条件时启用 802.1X/MAB。
- [ ] 控制面只暴露 22、53/67/69、80/443/4443；4443 只对引导网段放通；存储节点只暴露 4840/4421（按需限制来源）。
- [ ] `sudo kurrent host check --strict` 无 FAIL、无 SKIP；CA 私钥、`admin.conf`、凭据与审计文件为 600。
- [ ] 注册窗口按需开启并设置放行额度，用后关闭。
- [ ] TPM 证明强制保持默认开启；仅在过渡或排障时临时关闭，完成后恢复。
- [ ] 目标机开启 Secure Boot 并预置站点签名证书与 Microsoft UEFI CA；无 TPM 的设备不纳入池。
- [ ] 引导链产物来自签名构建（`build-sb.sh`），`/boot-assets` 的 `secureboot.status` 为 `ok`。
- [ ] 人员证书按需签发，离职或泄露立即吊销。
- [ ] 定期检查 CRL 刷新、凭据推送与审计告警。
- [ ] 备份加密保存，并验证恢复流程。
- [ ] 固件产物来自可信来源并校验 `SHA256SUMS`。
